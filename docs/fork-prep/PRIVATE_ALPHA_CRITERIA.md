# Private Alpha Criteria

## Purpose

Define a practical threshold for when the fork is ready for limited real-user testing.

## Private Alpha Goal

A private alpha should validate:

- that the inherited baseline is stable enough
- that the first layer of differentiation is visible
- that the product is useful enough to generate real feedback

## Minimum Technical Criteria

- [ ] Acquired core baseline has been signed off
- [ ] Supported source set is intentionally narrowed
- [ ] Active parsers have been validated with the parser matrix
- [ ] Major auth/link/scan flows are stable
- [ ] Basic failure visibility exists
- [ ] Critical provider dependencies are wired or intentionally stubbed

## Minimum Product Criteria

- [ ] Product identity is coherent enough to test
- [ ] There is at least one meaningful differentiation beyond the inherited product
- [ ] Ranking and/or filtering behavior is visible to the user
- [ ] Explanations exist or are planned clearly enough to discuss in testing

## Trust / Experience Criteria

- [ ] Users are not surprised by what the desktop app does
- [ ] If any centralized data behavior exists, it is explainable
- [ ] The product can be demoed without obvious broken-brand artifacts

## Recommended Alpha Scope

Keep alpha small:

- limited users
- limited sources
- clear expectations
- fast feedback loops

## What Private Alpha Is Not

Private alpha is not:

- broad launch
- final pricing validation
- final distribution readiness
- proof that every source is production-stable

## Exit Signal

You are ready for private alpha when the product feels:

- stable enough to trust for a small cohort
- differentiated enough to test your thesis
- narrow enough to support without chaos
